[ADR 0013](../adr/0013-p6-branches-transactions.md) r0.4 was accepted after:

- an independent review (4 blockers, 12 majors, 6 minors);
- a closure check (4 new majors);
- a re-check (R1–R4);
- a final check.

SPEC v1.6.8 mirrors it. Owner decisions:

- **D1:** branches are created explicitly; a session binds to the branch
  named like its git branch, otherwise `main`.
- **D2:** agents may merge, including into `main`; `require_certified`
  defaults to true.
- **D3:** the SD17 Conflict gate moves into P6.

P6 depends on P5b (SPEC §5). P5b's gate in turn waits on P5a and P4
(A11), so P6's gate cannot pass before them. Implementation may proceed
meanwhile. The live dogfood stores (protocol 3, op_log format 2) are
upgraded only after the P4 dogfood report (≥ 2026-11-04).

## Independent implementation review (2026-10-26)

Four non-implementing reviewers, one per area (kernel, merge and WHAT_IF,
service and protocol, store and migration), given ADR 0013, the SPEC and
the code only, looking for counterexamples. No blockers; 8 majors, 9
minors. Each finding below was checked by reading the code, and each
fix has a regression test that fails on the code before it (checked by
restoring the old file). ADR 0013 r0.7 and SPEC v1.6.9 record the
semantic ones.

**Majors (all fixed):**

- **Merge M1**: a default `require_certified` merge passed while it opened a
  Conflict on a revision other than the head (a base, a rule's conclusion),
  because the check read the head's status. The kernel and the oracle
  agreed. The same counterexample showed the ADR's R3 claim ("booleans never
  conflict with a single base") false through cross-branch dedup. A logical
  the merge opened a Conflict on is now CONFLICTED for the check; R3
  corrected. `p6_kernel_edges::require_certified_refuses_conflicts_off_the_head`
  (kernel = oracle).
- **Kernel K1**: an `ExpectHeads` after a `Merge` with an invalid read set
  was mapped to global ids twice: a wrong logical, or an index panic in the
  actor (admin `Raw` only). `late_invalid_read_set_in_a_merge_names_the_global_logical`.
- **Kernel K2**: branch digests left out the branch entry and received sync
  points that §3 requires, so replica checks could miss a divergent
  sync point, name or archive flag. `branch_digests_cover_the_branch_table_and_sync_points`.
- **Service S1**: a strict full check on a branch session issued its
  certificate from `main`'s database: NotCertified, or a panic once `main`
  renumbered. `anchors::strict_full_check_on_a_branch_issues_from_the_branch`.
- **Service S2**: the `ctx_commit` idempotency hash ignored branch, channel
  and principal, so another session's identical ops under the same
  `client_txn_id` received a result committed on a different branch.
  `p6_protocol::commit_txn_ids_are_bound_to_branch_and_principal`.
- **Service S3**: the hash included the session's cert id, so a retry of a
  durable commit got `TxnIdReuse` after a `ctx_check` re-issued the
  certificate, also after a restart (T18b).
  `commit_retry_survives_a_reissued_certificate`.
- **Store T1**: a group commit wrote projection rows read after the whole
  group (posts, base history, rule enabled), so they differed from a
  rebuild (PROP10); a historical read served by the projection after a
  restart returned a different answer. Older than P6 for posts and base;
  rows are now captured after each batch.
  `p6_review::group_commit_projections_equal_a_rebuild`.
- **Store T2**: `ctx migrate` interrupted after staging (or failing its last
  directory sync) lost the T68 list of changed epochs. Resume and rerun now
  derive it from the backup. `interrupted_migration_still_reports_changed_epochs`.
- **Store T3**: a rollback through `log.v2.bak` failed once a format-3
  binary had opened the store, because the old binary could not write the
  schema-2 projection tables. Format 3 keeps its projections in
  `projections.v3.sqlite`. Verified by reading the old open path; not run
  with an old binary.

**Minors:**

- Fixed: `MergeNotCertified` named the first failing logical in `certify`
  order, not by id (`merge_not_certified_names_the_first_failing_logical_by_id`);
  ValidationRecord conflict payloads did not identify the curvec (payload
  now starts with it; `validation_records_conflict_or_converge`);
  `ConflictingVersions` left with a branch-local id
  (`conflicting_versions_names_the_global_logical`); the 2→3 listing
  compared against a format-0 store's `acked_result` and listed every
  epoch (`format0_descended_stores_list_only_real_changes`); an unknown
  merge source was reported before the archived target (§9); an
  `expect_cert_valid` commit with no certificate returned an uncatalogued
  `NoCertificate` (now Refused with `Empty`); `ctx_branch` and `ctx_merge`
  took no `client_txn_id` (SPEC §6.5); `ctx_commit` writes were not counted
  as session writes (`branch_requests_take_txn_ids_and_errors_follow_the_order`,
  `ctx_commit_is_a_session_write`).
- Accepted, documented in ADR §4: a client-sent
  `ExpectHeads{source: Certificate}` is refused by the daemon before the
  kernel's §9 checks.
- Accepted: branch names also refuse a trailing `/` and `//` (stricter
  than §2, as git); `LogicalRef::New` in a merge batch's `ExpectHeads` is
  `UnknownRef` under the §9 order; a format-2 log with a torn tail must be
  reopened by the old binary once before `ctx migrate` (ChainBroken
  otherwise; no data lost).

Areas reviewed and found sound (the reviewers' own tests and a 400-seed
fuzz of `what_if` = commit and snapshot import = live): recursive
visibility, the id map and import retry, cross-branch dedup, failed and
dry-run batches leaving no trace, BRANCH_ONLY, per-branch certificates,
merge-base equivalence with the naive search and pruning soundness,
classification and the gate, the WHAT_IF journal (merges included),
validate-then-append with no gap, session binding, the observer per branch,
protocol lockstep, format-3 rows, idempotency persistence, snapshots with
pruned states.
