## Decisions (owner, 2026-11-06)

F1–F13 take the recommended option (a):

- **F1** one principal per OS user, mapped from the peer uid by a committed access document.
- **F2** the default lane is unchanged; each lane names its curators.
- **F3** crypto-shred through one key per content hash in an append-only key log; `ctx migrate` re-encrypts existing packs.
- **F4** the signed log head is deferred to its own ADR.
- **F5** G6 runs with two OS users on macOS (and Linux if the remote host allows).
- **F6** personal lanes do not egress by default; validators marked `local = true` are exempt.
- **F7** a merge needs authorisation (`MergeUnauthorized{count}`).
- **F8** non-owner principals use MCP only in P9.
- **F9** `ctx ui` uses a per-launch token in multi-user mode.
- **F10** proof of possession: non-owner commits carry the bytes of every content hash they introduce.
- **F11** branches record their creator.
- **F12** the store owner sees everything.
- **F13** a principal holding the exact bytes may learn they were shredded.

**F14**, in the owner's narrowed form:

- A merge into the merger's own branch transports every mergeable change; reads still go through the ACL.
- A merge into `main` or a branch the store owner created needs the store owner for an actual Policy change.
- ValidationRecords keep their exact `(rule, curvec)` and their original validator source.
- CodeAnchor objects arrive not base and `unobserved`.
- Every other change is checked as its direct op: Curate, rule premises, artifact targets.

## Implementation milestones

1. **Done.** Principals and transport (ADR 0017 §3; T58, T98, T99).
   - **Reserved ids** (`PrincipalId::is_reserved`, `is_store_owner`): 0–15 and `0x5641_xxxx`. Document ids start at 16.
   - **The uid mapping** (`principals::PrincipalMap`): the store owner's uid gets the socket's channel principal, as before. A mapped uid gets its principal, on the agent socket only. Any other uid is closed before a byte is read.
     - The mapping is checked again on every request; a revoked or remapped uid gets `AccessRevoked` and the connection closes.
     - In milestone 1 the mapping is set by `Daemon::set_principals`; milestone 2 feeds it from the committed access document.
   - **Socket layout:**
     - `run/shared/agent.sock` (directory 0711);
     - `run/private/{observer,admin}.sock` (0700);
     - the public `run/shared/endpoint` record (0644: protocol, socket name, owner uid).
     - The agent socket is 0600 in single-user mode and 0666 once another principal is mapped.
   - **Entering multi-user mode** (`set_principals`) first requires the file-system rules (`contextdb-proto::fsguard`):
     - every entry owned by the daemon's uid, private modes, and no ACL (deny-only included);
     - the ancestors owned by root or the owner and not writable without the sticky bit;
     - every mapped uid able to search down to the shared socket;
     - the sockets inside `<data>` (the long-path fallback is refused).
     - Violations are returned by name, and the agent socket stays closed.
   - **File modes:**
     - the store layer and the outbox create directories 0700 and files 0600 explicitly;
     - `ctxd`, `ctx`, `ctx-hook` and `ctx-mcp` set `umask(077)`;
     - the launchd plist has `Umask = 63` and the systemd unit `UMask=0077`;
     - `ctx doctor <dir> --fix-modes` repairs modes and strips ACLs (macOS through `exacl`, Linux through the POSIX ACL xattrs, so no libacl is needed), and never changes an owner.
   - **Clients:** `Client::connect_shared` (and `ctx-mcp` for a data directory the caller does not own, `--data` or `CTXDB_DATA`) reads the endpoint. Before sending anything it checks that:
     - the endpoint's owner uid equals the owner of `<data>`;
     - the ancestors pass the ownership rule;
     - the socket's peer uid is the owner.

     Otherwise `ServerNotOwner`.
   - **The non-owner allowlist** (`service::non_owner_allowed`): the requests `ctx-mcp` sends. Everything else is `ChannelRestricted` (`Status`, hooks, observer and admin requests).
   - **Sessions and handoffs:**
     - sessions are bound only by their principal: `SessionOfAnotherPrincipal` for session ids and claimed call ids;
     - harness keys are per principal, also after a restart;
     - `ctx_handoff_begin{to}` names the accepting principal; unnamed handoffs stay within the sender's principal;
     - listing and accept show only handoffs addressed to the caller;
     - the accept reports `dropped_unauthorized` and validates only what it copied.
   - **Protocol 7.**

3. **Done.** Reads (ADR 0017 §5).
   - **The redaction point** (`contextdb-daemon::redact`): `Service::handle` sends every response to a principal other than the store owner through `Viewer::redact`.
     - The viewer judges `Authorized(p, l, b)` once per logical, through `BranchView::authorizes` (the kernel's access document, the branch's `dirs`). A rule is whole only if its conclusion, premises and references are all visible.
     - The branch is the one the request reads: the bound session's, the one `OnBranch` named, or the one `ctx_changes` resolved. Ids are resolved on the newest snapshot, so a commit's own allocations are found.
     - The pass is total: a response type a non-owner cannot receive becomes `ChannelRestricted`. The store owner's responses are returned as they are, with no `redaction`.

   **Deviations from ADR 0017 and open items:**
   - **Counts travel in the envelope**, not inside each response type. Commit results, merge reports and certificates are durable values, and their encodings stay unchanged; one `redaction` record per response carries what §5.4–§5.6 count.
   - **WHY lists a rule when at least one of its premises is visible**, without the rule's other premises. Explanations name rules, not their premises. Per-rule premise counts are given for the witness rule, whose premise proofs are the only ones shown, and for WHY_NOT failures.

4. **Done.** Writes (ADR 0017 §6).
   - **Kernel checks** (`txn.rs`, `Authorise`): they run inside the transaction for every kernel batch (commit, `what_if`, `ImpactBatch`), against the kernel's access document and `batch.principal`.
     - **Order.** A logical ref that resolves is checked first, so a hidden logical answers `Unauthorized(Read)` whether or not the revisions the op names exist. The other refs resolve next; then comes `Read` on everything the op names, then the role (`Write` or `Curate` in `entry(lane)`), then the channel.
     - **Rules.** Create: a writer, and a curator for a base. Revision, head, metadata: read and write. Bases: read and curate. Rules (`AddRule`, `Rebind`, `SetRuleEnabled`): read the conclusion, every premise and every reference, and write the conclusion's lane. Artifacts: read and write the target. `RecordValidation`: refused (`Curate`). `ExpectHeads`: read.
     - **Errors.** `Unauthorized{op_index, reference, need}`, where `reference` is the ref as written. `InvalidLane` for `personal:<unlisted>` covers the store owner too, while an access document exists.
     - **Who is checked.** Non-owner batches skip the kernel's fast path, so they always reach the checks. The store owner (any reserved id) passes every check. A single-branch `Db` outside the kernel checks nothing (`auth: None`), and neither does the store's replay of `main`.
   - **Branches** (rule 6):
     - `BranchInfo.creator` comes from the creating batch's principal, the store owner's class for reserved ids. It is in snapshots as a trailing section; older format-5 snapshots lack it and are rejected (replay).
     - Commits, merges and archives on another principal's branch are `BranchOfAnotherPrincipal`. Owner branches take every writer's commits, and only the store owner archives them. A fork writes nothing to its parent and is open to anyone.
     - Auto-binding (`resolve_branch_for`) binds a git branch's namesake only if the session's principal or the store owner created it.
   - **Merges** (rule 7, `kernel_merge::refusals`): after classification and before the plan, a non-owner merge into `main` or an owner branch counts every applied change failing its class:
     - a policy that actually changes;
     - new logicals (writer) and new revisions (read and write, plus curate when they arrive as base);
     - heads and metadata (read and write; `dirs` must narrow);
     - existing base bits (curate);
     - new rules and changed enabled flags (read everything named, write the conclusion's lane);
     - new and changed artifacts (read and write);
     - the Conflicts the merge opens (read each side).

     ValidationRecords and CodeAnchor objects are transported unchecked. Any failure refuses with `MergeUnauthorized{count}`. A merge into the merger's own branch is not checked.
   - **The oracle reference** (`contextdb-oracle`) is written independently:
     - `InputModel::apply_authorised` lists each op's reads and roles and takes the first unmet one;
     - `BranchOracle` applies the branch rules as a table, and the merge rule as a diff of the merged target against the target.
   - **Daemon:**
     - **Proof of possession** (`Service::possession`) for every content-hash field of a non-owner's batch in `ctx_commit`, `ctx_what_if` and `ImpactBatch`, which now carry `blobs` (protocol 7). A hash without matching bytes, and not on a revision of a readable logical, gets the same `MissingBlob` as an unknown hash.
     - **`ctx_record` / `ctx_supersede`:** a dep naming a hidden logical is `Unauthorized(Read)` before any other answer (no head hint, no "does not exist"); `carry_rules` over a hidden premise is refused with the reference `carry_rules`.
     - **Error details** of `Unauthorized`, `InvalidLane`, `MissingBlob`, `MergeUnauthorized`, `BranchOfAnotherPrincipal`, `HeadConflict` and `ReadSetConflict` reach non-owners.

   **Deviations from ADR 0017 and open items:**
   - **Replay re-runs the checks.** The kernel always authorises, and replay goes through the same deterministic predicate against the same staged access document, so a batch valid at its epoch stays valid. §6.1 says replay never re-checks; the outcome is the same. A batch a pre-milestone-4 build accepted from a non-owner (tests only: no deployment had multi-user mode) could be refused on replay.
   - **`Unauthorized.reference` is text** (`key`, `logical N`, `rev N`, `rule N`, `artifact N`, `new rev K`) in `TxError`, which has no wire form. The daemon passes it through as the error detail. For deps the op index is the dep's position.
   - **`RecordValidation` by a non-owner** is `Unauthorized(Curate)` in the kernel. The daemon already refuses it on the agent channel (`ChannelRestricted`).
   - **The read check covers every revision an op names** (for example both revisions of `SetHead`), not only its logical. A hidden revision is then never confirmed by `LogicalMismatch`.
   - **`InvalidLane` needs an access document.** Without one, personal lanes have no special meaning (T106).
   - **A squatted branch name is skipped silently**: the session binds `main`. The report to the session (§6.2 rule 6, "skipped and reported") is not built.
   - **Proof of possession scans the branch's revisions** for a hash sent without bytes (linear). G5 measures it.
   - **Two pre-existing oracle differences surfaced, unrelated to authorisation.** `BranchOracle` refuses an `Existing` id naming a revision staged earlier in the same batch, and on branches it reports `DuplicateRule.existing` and merge cycle paths differently. The direct-op property therefore compares against `InputModel` on `main`, and the merge property compares non-authorisation errors by variant. These belong to the P6 oracle and are left as they are.
   - **Multi-user mode is still not offered by `ctxd`.** Egress (milestone 5) and crypto-shred (milestone 6) come first, then G6's real two-user run.
5. **Done.** Egress (ADR 0017 §7).
   - **The rule** (`contextdb-core::access`): `egress(lane)` is the lane entry's flag, so personal lanes follow `[personal] egress` (default off, F6). Without an access document every lane egresses, as before P9. `mirrored(lane)` adds, when the document maps a principal besides the owner, that every principal reads the lane: members `*members`, no grants, no denies. Neither enters `Authorized`.
   - **Validators** (`validators.toml`): `local = true` on a `command` validator; a `claude` validator with `local` is refused at load.
     - A rule job reads the conclusion's lane and each changed premise's lane, and a pair reads its two sides' lanes. When one of them has egress off, the work goes to the first matching validator marked `local`.
     - If only non-local validators match, the work is skipped with no attempt counted. A job stays `Queued`; every claim looks at it again, so it runs as soon as egress turns on or a local validator is loaded. A pair is postponed; a `SetAccess` (seen by discovery) or a reload makes every postponed pair due (`Candidates::judge_wake`).
     - The worker checks again on the snapshot it builds the task from; if egress turned off meanwhile, the job or pair is given back (`Ran::SkippedEgress`).
     - `ctx validators status`: `skipped_egress` (queued jobs blocked now) and `pair_skipped_egress` (postponements).
   - **The embedder:** fill embeds a content only for a live head in an egress lane, and drops, before each batch, a content no egress lane carries under the current document. The vector ranker and embedding candidates skip heads in non-egress lanes (`BranchView::egress`), so a vector computed through another logical with the same content is not used for them.
   - **The mirror:**
     - `render` skips lanes that are not `mirrored`, under the access document of the kernel it renders. A replayed render at a tip's epoch therefore uses that epoch's document, and tips still validate.
     - A commit whose parent had files of a withheld lane carries `Ctx-Egress-Removed: <lanes>` and a report line saying the bodies remain in older commits.
     - In multi-user mode export refuses a repository whose common `.git` directory has group or other read bits (`MirrorReadable`), unless `MirrorAction::Export{readable_ok}` (`ctx mirror export --readable-ok`).

   Tests (`contextdb-daemon` `p9_egress`, T105):
   - a recording validator: a job with a premise in a non-egress lane is skipped by the remote validator with no attempt, then runs on a local one added behind it; with egress turned on it runs remotely; without an access document both jobs run;
   - the judge: a pair in a non-egress lane is postponed for a remote judge (no call), woken by the `SetAccess` that turns egress on, and taken by a local judge while egress stays off;
   - a recording embedder: no text from a non-egress lane is sent (a shared lane with egress off, and a personal lane); the shared-content vector is not ranked for the non-egress head; no embedding pair touches one; egress on embeds the lane, the personal lane stays off;
   - a real repository: all lanes without a document; after the document, only the shared egress lane, with `Ctx-Egress-Removed`; `MirrorReadable` for a 0755 `.git`, accepted at 0700 or with `readable_ok`; the uncached tip validates by replay.
   - Mutation check: removing the validator choice, the ranker filter or the mirror filter makes every test fail; with only the choice removed, the second check before the call still stops the job.
   - `validators.toml`'s `local` has a parser test.

   **Deviations from ADR 0017 and open items:**
   - **"Multi-user mode" for the mirror** is read from the committed document (another principal mapped), not from the daemon's `Options::multi_user`, so the render stays a function of the log. Single-user documents still withhold non-egress lanes (G-EGRESS).
   - **`Skipped{egress}` is not a job state.** Jobs stay `Queued` and are counted at status time; pairs are postponed rows. The ADR's re-queue happens by construction for jobs and through `judge_wake` for pairs.
   - **`judge_wake` also cuts short the back-off of failed pairs**, on a `SetAccess` or a reload.
   - **A body already sent stays sent.** The checks run on the latest snapshot before each call; a `SetAccess` that commits during a call does not recall it (§2.3).
   - **The `.git` check reads modes only**, not ACLs. Who can read the repository remains the owner's responsibility.
   - **`ctx mirror export --rebuild`** (dropping the bodies from older commits) belongs to milestone 6 (§8.5).
6. Crypto-shred and migration (ADR 0017 §8, §10), in parts.
   - **6a, done: encrypted packs and the key log** (§8.1, §8.2).
     - **Records:** `CXBE | len | content_hash | nonce 24 | XChaCha20-Poly1305(key, nonce, plaintext, aad = content_hash)`. New segments start with `CXPH\x01`; a scan resyncs at the next magic of either record type, as before. A record is valid when it authenticates under its hash's key, and a read decrypts and then checks BLAKE3.
     - **The key log** (`contextdb-store::keys`): `keys/keylog-NNNNNNNN` segments with a checked header (kind `Append` or `Generation`, `purged_through`) and `CXKY` records. Keys load from the newest generation and every later segment; the last record for a hash wins. Each process appends only to a segment it created.
     - **Durability:** `stage_blobs` appends the new keys with an ordered sync before the pack records, and `put_blobs` fully syncs both. A key left by a crash before its record is reused.
     - **Open:** key segments are synced and loaded before the pack scan.

     Tests (`contextdb-store` `p9_packs`):
     - no file in the store holds the plaintext;
     - an acknowledged payload reads back after a power cut, over 64 seeds and every tail fate; a payload staged but never committed is absent or whole;
     - without its key a payload is absent and a commit naming it is `MissingBlob`; a record relabelled with another hash fails authentication.

     Two tests that corrupt a pack at a fixed offset now use 72 (segment header plus record header). The full workspace suite passed on the remote Linux host.
   - **6b, done: `ShredContent`** (§8.3).
     - **The op:** tag 21, admin only, global, batches of `ShredContent` alone (`SoleOpRequired`), committed on `main` and never dry-run (both `ChannelRestricted`, with the reason in `op`). The kernel's shredded set lives in the kernel and in format-5 snapshots, as a trailing section.
     - **The checks:** `ContentShredded{content}` comes before `MissingBlob` for `CreateLogical`/`AddRevision` content, `RecordValidation.meta`, `OpenArtifact.payload_hash` and `ResolveArtifact.note`. `stage_blobs` refuses shredded bytes.
     - **Reads:** `Unavailable::Shredded` comes from the store's pack index, refreshed after each durable group and at open. `Response::Read` carries `unavailable` (`missing`, `corrupt`, `shredded`), and `ctx-mcp` passes it on.
     - **The daemon:** `Request::Shred{key, rev, with_reviews, confirm}` lists the targets and commits with `confirm`. A shredded hash never proves possession without its bytes. `ContentShredded` details reach non-owners.

     Tests:
     - `contextdb-store` `p9_shred`:
       - T59 (store half): refusals, unchanged digests and statuses, `Shredded` before and after a restart and from a snapshot, re-sent bytes and later ops refused;
       - **PROP16:** random multi-branch histories (`branch_gen`) with random shreds, against the same history without them. Results are compared modulo the epoch; every branch's inputs (epochs renumbered), statuses and fork epochs are compared; payloads are `Shredded` for exactly the shredded contents; replay from the log, and half the seeds from a snapshot, agrees. Default 300 seeds (`CONTEXTDB_P9_SHRED_SEEDS`).
     - `contextdb-daemon` `p9_writes` `t59_t107_shredded_payloads`: the plan across branches, `with_reviews`, refusals, the read's `unavailable`, an unchanged status, and T107's shredded rows for a non-owner and the owner.

     **Deviations:**
     - **PROP16 compares more than digests.** Digests include epochs, so after renumbering it compares every input, status and fork epoch. The one exception is the payload hash of a merge's Conflict artifact, which names the merge epoch (ADR 0013 §6.2). "`doctor` agrees" waits for 6c.
     - **The oracle checks only the structure** of shred batches (sole, admin, `main`, not dry-run). The shredded set and `ContentShredded` are checked against the store by PROP16.
     - **Resolution notes for `--with-reviews`** are found by scanning the op_log, since artifacts do not keep their notes.
   - **6c, done: the purge** (§8.2, §8.4).
     - **The shred record** in the kernel now maps each hash to its shred epoch, carried in snapshots, so every part's progress is an epoch (`purged_through`).
     - **The key log** (`Store::rewrite_keys`) is rewritten after the group's full sync, inside the commit, on the writer thread:
       1. `keylog-<n>.tmp` with a `Generation` header (`purged_through` = the last shred) and every other key, synced;
       2. renamed, then `sync_dir`;
       3. every older segment and `.tmp` unlinked, then `sync_dir`.

       Only then does `key_log_purged_through` move. At open, the rewrite runs again if the newest generation is behind, a shredded key is loaded, or a `.tmp` or an older segment is left. A failed rewrite leaves the mark behind, and the next open or shred retries it.
     - **The projections** (`contextdb-store::purge`): `secure_delete`, a one-row `ctx_purge` table and `wal_checkpoint(TRUNCATE)`.
       - Recall re-indexes the touched logicals and runs FTS5 `optimize`.
       - Vectors delete every model's vector of the content and evict the cache. A `vectors.sqlite` left by a disabled embedder is opened and purged too.
       - Jobs whose rule's conclusion, asserted premises or current vector carry the content become `JobState::Skipped` (new state 5), with `outcome_meta` and `last_error` cleared and the token bumped.
       - Pairs with such a side become judge state Skipped, with label, meta and error cleared.
     - **`Service::purge`** runs after a shred commits (it decides `purged`) and at `ctxd` start. `ctx status` shows `purge_pending`, the shred epochs above the lowest mark.
     - **Races:**
       - the indexer and the embedder check the store's live shred set while holding their projection's lock, right before writing;
       - workers check it after the call and before committing (`Ran::SkippedShredded`).

     Tests:
     - `contextdb-store` `p9_shred` T103: the rewrite stopped after each of its five steps, and power cut under three tail fates over six seeds. The durable disk is read before reopening: once the rewrite reported completion, no file in `keys/` holds the key. After recovery the key is gone, the payload is `Shredded` and other payloads read back. A mutation that drops the final `sync_dir` is caught: an old generation comes back.
     - `contextdb-daemon` `p9_shred`:
       - after `purged`, a scan of every file in the data directory (except `sessions/`, outside G-SHRED), including `-wal` files, finds no shredded text. Mutations dropping the recall re-index or the WAL truncation are caught, in `recall.sqlite` and `recall.sqlite-wal` respectively;
       - a shred committed with no purge is pending in `ctx status` and purged at the next start;
       - the purge marks a queued job `Skipped`;
       - a validator call in flight at the shred commits nothing and leaves the job `Skipped`.
     - `p9_writes` T59 now expects `purged: true`: the purge now completes inside the shred request.
     - The full workspace suite passed on the remote Linux host. The first run caught that stale T59 expectation; after the fix, `p9_writes` and PROP16 were rerun there. PROP16 passed at 10,000 seeds (46,253 shredded, 28,046 dropped, 9,023 multi-branch).

     **Deviations:**
     - **A small window between the check and a validator's commit.** The token fence checks the shred set just before the commit, not atomically with it.
     - **The scan checks the data directory's files, not raw free blocks of the file system**, which no user-space test can read.
     - **"`doctor` agrees"** (PROP16, §8.2's key check) needs the doctor changes of 6e.
   - **6d, done: the mirror** (§8.4 item 5).
     - **`MirrorStale{PayloadGone}`** (code `MirrorStale`) for a ref whose history holds a blob whose body, or whole text, hashes to a shredded content. `--force` does not override it, since its backup would keep the payload. The check runs before tip validation, so a replayed render, which now shows the placeholder, never makes such a tip look `MirrorModified`.
     - **The clean cache.** A history found clean is cached per (repository, branch) with the last shred epoch it was checked against. A commit written on a clean parent is clean, since its tree is rendered after every shred in the snapshot. A new shred, a different tip or a lost `mirror.sqlite` causes a rescan.
     - **A deleted ref** is not recreated on a cached commit that holds a shredded payload; the export starts a fresh history.
     - **`--rebuild`** (`MirrorAction::Export.rebuild`) writes one parentless commit of the current render, moves the ref by compare-and-swap whatever it held, and deletes every `refs/contextdb-backup/` ref. It reports the `git reflog expire --expire=now --all && git gc --prune=now` command and does not run it.

     Tests: `p8_mirror` T103:
     - after a shred, export is `MirrorStale`/`PayloadGone`, with and without `--force`;
     - a deleted ref comes back as a fresh one-commit history;
     - the backup ref still holds the text until `--rebuild`;
     - after it, the ref has one commit, no backup ref is left, no blob reachable from `refs/contextdb*` holds the text, and the shredded record renders as the placeholder;

     Two mutations are caught: never reporting `PayloadGone`, and hashing only the whole file (front matter included), not the body. The full workspace suite passed on the remote Linux host.

     **Deviations:**
     - **`--rebuild` discards hand edits on the ref without a backup.** A backup would keep the payload, and `ctx mirror proposals` can be run first.
     - **Only the exported branch's ref is checked.** Other branches' refs report `PayloadGone` at their own export, and `--rebuild` deletes the backup refs of every branch.
   - **6e, done: `ctx migrate` to format 5** (§8.5, §10).
     - **`contextdb-store::migrate5`** runs steps 0 to 7 under the store lock. `migrate::migrate` decides step 2 from the log, never from the marker. A store with no commit yet (an empty `log/`) counts as current.
       - **Step 3** re-encrypts each plaintext pack segment and loose blob file into a new segment. Keys come first, each in an `Append` segment, synced. The copy is read back and every record decrypted before the old file is unlinked and the directory synced. Shredded contents (from the log's `ShredContent` ops) are dropped.
       - **Step 4** checkpoints each body-bearing projection with `TRUNCATE`, writes it `VACUUM INTO` a fresh file, and stamps that file (`ctx_format.rebuilt_at_format = 5`, `secure_delete` on). It then unlinks the old `-wal` and `-shm` and renames the fresh file into place.
       - **Step 5** is the caller's `Modes`: `ctx` applies `fsguard::fix_modes` and checks with `fsguard::walk`.
       - **Step 6** checks the disk:
         - the log is current with no swap;
         - no plaintext segment or loose blob is left;
         - every content the log names, except shredded ones, is in an encrypted record with its key;
         - there is no key-log `.tmp`;
         - every projection is stamped, with no `.migrating` file;
         - the modes pass.
     - **Openers.** `Store::open` refuses a marked store with the first step whose cheap check fails, or 6 when none does. Without the marker it refuses a plaintext segment or loose blob (3) or an unstamped projection (4). `doctor --truncate-before` refuses a marked store. `ctxd` and `ctx` print "run `ctx migrate` again". `StoreError::MigrationIncomplete` now carries `step`; the old swap case is step 2.
     - **New projection files** are stamped as their first write (`purge::is_fresh` before the connection opens).
     - **A segment counts as plaintext** only if it holds a valid plaintext record, so a torn or garbage segment left by a crash is not mistaken for one.
