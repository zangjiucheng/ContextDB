   - **bm25 windows.** bm25 scored every row a query matched, so a term most records hold cost time linear in the store (at 10⁵ records with Zipf words: idle p99 152 ms, 280–370 ms under a commit stream; with the dense 40-word vocabulary 578–818 ms, and a 6.5-hour 10⁵ fill, because lexical candidate generation was quadratic in a backfill). Matches are now ranked in windows of 2,048 rows by row id `(logical << 16) | branch`, bm25 order within a window; paging walks every window. Row ids depend only on the row, so a rebuild gives the same windows (review M2); an older `recall.sqlite` is rebuilt on open.
   - **A reader connection and one snapshot.** Recall reads `recall.sqlite` on its own read-only WAL connection, so an index write never delays it, and every bm25 page of one recall comes from one read snapshot (review M1).

   - **Mirror.** A cached tip is checked against the log (`MirrorStale` after a truncation), also when the ref was deleted (review m4); a failed ref update is `MirrorRaced` only when the ref moved, otherwise `MirrorFailed`.

### G3

[`p8-g3-properties.txt`](p8-g3-properties.txt) (`scripts/g3-p8.sh`, remote Linux host, 2026-11-06, final tree): **PROP14** at 10,000 seeds passes, plus the injective-path property.

- Each seed is a `generate_p7` history: half committed on `main`, the rest on a fork `dev`. Every content hash gets a text body.
- Random queries, modes, limits, kind filters, budgets and levels check:
  - labels against the oracle on `main`, and against the kernel's per-branch labels (checked by PROP13) on `dev`;
  - exactly `min(limit, |eligible matches|)` items, so a page is short only when the eligible set is exhausted;
  - withheld entries are ineligible and at most `limit`;
  - a budget keeps labels and order;
  - the same result, as a set with statuses, after `ctx reindex`.
- Metamorphic checks: lane `""` equals lane `"repo"`, and an unrelated record never removes a certified exact-key match.
- Counts: 120,000 queries, 155,519 items (134,284 Certified, 14,872 Stale, 5,178 Pending, 1,185 Conflicted), 21,779 withheld, 96,619 short pages, 59,868 budgeted, 60,000 on `dev`.

Limit: PROP14 uses an in-memory index, and its stores never reach 2,048 matches for a query. It therefore exercises neither the reader connection nor more than one window (review M1, M2). The `recall` unit tests above cover those.

### G6

Retrieval on this project's three dogfood stores, 2026-11-06 (`p8_g6`).
- Embedder: Ollama `nomic-embed-text` (768 dimensions) through `scripts/ollama-embed.py`.
- Token counts: `claude -p` (`claude-haiku-5-5`).
- Queries: 120 natural-language queries (21, 54 and 45 per store) by labelling agent A, who read every live head on `main` (`p8_g6 export`).
- Labels: agents A and B each labelled the relevant keys independently; neither saw any system output.
- Raw queries, labels and outputs contain project text and stay out of the repository. [`p8-g6-score.txt`](p8-g6-score.txt) has only the aggregates.

| System | Agreed relevance (both labellers): recall@5 / recall@10 / MRR | Lenient (either): recall@5 / recall@10 / MRR |
|---|---|---|
| key only | 0 / 0 / 0 | 0 / 0 / 0 |
| key + FTS | 0.706 / 0.805 / 0.769 | 0.644 / 0.749 / 0.801 |
| hybrid | **0.710 / 0.820 / 0.770** | **0.657 / 0.771 / 0.822** |

- The labellers' relevant sets agreed exactly on 68 queries and differed on 52. Every query had at least one key both agreed on.
- **Key only scores 0** because the queries are natural-language sentences, and the key ranker matches only a key equal to the query, starting with it or containing it. It serves agents that already know a key or a key path.
- **Hybrid against key + FTS.** Hybrid is slightly ahead on every measure. With 120 queries the difference is within noise: hybrid helps, but not by much on stores of this size (at most a few hundred heads each).
- **Token cost** (packed recall at the outline level, summed over 120 queries, `bytes/4`):

  | Budget | Tokens returned | Relevant records included | Relevant full bodies |
  |---|---|---|---|
  | 1,000 | 110,870 | 237 of 349 | 271,333 tokens |
  | 2,000 | 117,552 | 237 of 349 | 271,333 tokens |
  | 4,000 | 117,552 | 237 of 349 | 271,333 tokens |

  Ten outlines fit within 2,000 tokens, so larger budgets change nothing at `limit` 10. The packed responses cost 41–43% of reading the relevant records in full and include 68% of them.
- **`bytes/4` against real tokens.** On 10 sampled bodies, the estimate was 0.57–0.78 of `claude -p`'s count (median 0.61). `bytes/4` therefore **undercounts by about 40%**, and a budget in real tokens is overrun by up to 1.6×.
  - The method: the extra input tokens over an empty-body prompt of 833 tokens.
  - The estimate is labelled `bytes/4 v1` in every response, so a calibrated `v2` can replace it without changing the meaning of old responses.
  - Follow-up: replace the estimate (for example `bytes/2.5`, or a tokenizer table).
- **`min_cosine`.** The nearest-neighbour pairs: 132 pairs (each Decision, Plan and Fact head with its three nearest neighbours in its lane at cosine ≥ 0.55). Both labellers labelled them: 130 agreed, 6 of them conflicts, and 2 disputed.
  - No threshold separates contradictions well. The best F1 is 0.17, at 0.77.
  - At the default 0.82, 7 pairs are kept and 1 of the 6 conflicts is found.
  - Cosine measures topic, not contradiction. The default stays 0.82, so embedding candidates stay few and an LLM pair validator does the judging.
  - The 6 conflicts are too few to calibrate on; this is redone when real conflicts accumulate.
- Caveats (review m6):
  - Token cost uses the eval's own `bytes/4` sum, not the response's `estimate` field.
  - The real-token sample takes the first bodies by key in each store, measured inside the validator prompt; JSON escaping inflates the count a little.
  - The `min_cosine` recall is relative to pairs at cosine ≥ 0.55.
  - The ADR's comparison with P4's recorded reads is not implemented; follow-up.
