SPEC is authoritative for these contracts; the ADR preserves the alternatives and reasoning.

## G5 — Budgets

Initial ADR-calibrated budgets, measured with the workload and fsync/copy-on-write costs reported:

- Import 10,000 entries into the replica in ≤60 s on the remote Linux host.
- Join 10,000 entries with 10 open branches in ≤120 s; report copy-on-write memory.
- Catch up one entry on 10 open branches in ≤50 ms; report op_log batches, fsyncs and memory.
- Publish ten proposals to a local remote with ≤2 s added to `git push`.
- Add ≤20 ms to `git commit` through `reference-transaction`; a team-ref fetch's durable announce and ACK add ≤50 ms.
- Compact and join 100 MiB of team state; report time and peak memory, including the streaming verification buffer separately from resident state.
- Recall p99 with 10⁴ mirrors stays within +10% of the baseline with the same record count.

## G6 — Real use

First use two clones, two signing keys and a bare remote on one machine. Then use a real team remote with agents on both edges for **at least five days**, **at least 50 accepted entries** and **at least two members**. Record:

- Equal team digests checked daily.
- Zero lost proposals: each ends accepted, rejected, conflicted or dropped.
- Probe records depending on every changed team record, read after each fetch: every supersede/retraction invalidates the other edge within one fetch.
- Zero code pushes blocked by publish or ReplicationLag under the default policy.
- No ReplicationLag persisting beyond one fetch after the last import.

## Implementation notes

Clarifications made while implementing milestone 1. They fix details the ADR and SPEC leave open and do not change any guarantee.

- **`Ref` names its revision.** A team rule's reference is `Ref(content)`, like `Pin(content)`: the kernel's `Ref` edge targets a revision, and a rule's identity must not depend on the replica's state.
- **Genesis carries a `batch`.** Generation 0's first entry has the ordinary tree with one proposal whose only op is `SetTeamAccess{doc}`; it is signed by an admin of that document. Every entry is parsed the same way.
- **The Compact reserve is a proven bound.** Where the future `Compact`'s accepted id lands among the sorted items changes the next-fit chunk packing. Next-fit gains at most one chunk when one item is inserted anywhere, so an ordinary proposal is accepted only if `ckpt_size(Σ) + item(64-byte member) + 44 ≤ state_bytes` (one item and one index entry). Then `ckpt_size(Σc) ≤ state_bytes` for every `Compact`, whatever its id and author.
- **git ≥ 2.44 for partial clones.** `ctxd` reads team objects with `GIT_NO_LAZY_FETCH=1`, so a partial clone reports missing blobs (`ReplicaIncomplete`) for the hook to fetch by id in the user's environment (§8.1). Older git ignores the variable and would try the promisor itself, without credentials or a terminal; it fails instead of hanging, and the import stays incomplete until a newer git or `ctx team sync` fetches the objects.
- **The decision log is the replica's durable form.** `<data>/teams/<id>/log` holds every decided entry with the bytes `accept` read, framed and checksummed; open replays it through `accept` (deterministic), cuts a torn tail, and import fetches what is missing from git. Snapshots of the replica (the checkpoint encoding) are a later optimisation, measured against the G5 join budget.
- **Admission details the SPEC leaves open (milestone 3).**
  - A mirror as a local rule's conclusion is `ReplicaReadOnly` (SD21.7 and the §6.2 P10 order), checked before the canonical rule checks; §2.5 A1's `ForbiddenConclusion` wording is superseded for replica origin.
  - No artifact of any type may target a mirror (`ReplicaReadOnly`), not only Conflict sides: only the replica channel writes mirror state, and an artifact a merge carried could otherwise land where its target is invisible. The P7 judge targets the local side.
  - "Rebind target" means a rule whose conclusion is a mirror. Rebinding a local dependent onto a newer mirror head is the intended recovery for `Cur` (ADR §5.3).
  - A replica-origin create outside its own team's namespace is `InvalidKey` (key) or `InvalidLane` (lane). ReservedNamespace applies in the multi-branch kernel only; the team replica's plain `Db` keeps its `team/` keys with Local origin and its own A5.
  - `gap = true` on a scope that is not `team:` is `ChannelRestricted`. The replica channel may not run `ExpectHeads`, branch ops or merges (`ChannelRestricted`).
  - The shred exemption also skips `MissingBlob` for a replica write of shredded content: its bytes are gone, and the revision reads unavailable.
  - A replica `SetMetadata` with non-empty `dirs` is `InvalidMetadata`: only tags are mirrored (Q9).
  - The kernel does not check that a replica batch's principal is the store owner; no client socket maps to `Channel::Replica` (transport trust, as for the observer).
- **MirrorAttach mechanics.** `head` is a content hash; the op brings in the logical and its head revision only (other revisions arrive by replica `AddRevision`, a dedup import) and adds nothing to `Allocations`. If no branch holds a revision with `head` yet — a branch caught up alone, ahead of the others — the attach creates it, as a replica `AddRevision` would (`MissingBlob` unless its bytes are present or shredded); otherwise it imports the existing one. A key already visible on the branch is `LogicalExists`; a key with no replica-origin logical is `UnknownRef`; both are decided after the channel check, so a non-replica caller learns nothing about keys. (PROP19 at 10,000 seeds found the first version, which refused a head no branch held, failing such a catch-up.) In a batch that attaches, logicals are named by `New(k)` or key: an invisible global logical id is `UnknownRef` there (the kernel's `Existing(next + i)` convenience for fresh logicals is not available when attached and fresh logicals interleave; the oracle never had it).
- **op_log format 6.** Format 6 keeps format 5's frame layout; what it adds is permission to log the P10 encodings (the replica channel, a replica-origin create, MirrorAttach, a gap watermark), which a format-5 build refused as `CapacityExceeded{Encoding}`. The 5 → 6 migration changes only the log: batches, batch hashes, idempotency records and frame checksums are unchanged, the old log is kept as `log.v5.bak`, and packs, keys, projections and modes stay format 5's. A format-6 build opens a format-5 log only after `ctx migrate` (T119, `crates/contextdb-store/tests/p10_migrate.rs`). The legacy fixture writer now replays through the kernel, so fixtures can hold branches and merges.
- **Merges and mirrors.** A merge takes no replica-origin state (head, base, tags, revisions, visibility) and makes no mirror visible; a mirror's artifacts (none can exist) are excluded as a defence. After classification and authorisation (`MergeUnauthorized`) and before the plan, a carried rule whose premise or reference is a mirror revision the target cannot see, or a taken ValidationRecord whose curvec names one, is `MirrorLag` (the SPEC names rules only; a validation would otherwise land with an invisible curvec). Merge-time A5 exempts mirrors by origin, as commit-time A5 does — PROP13 caught the oracle missing this exemption on its first 300 seeds.
- **Proposals and publish (milestone 4).**
  - The local layer replies alike for a record its author cannot read and for one that does not exist: `Unauthorized(Read)` naming only what the author named. The one exception is creating a taken key (`LogicalExists`, SPEC's global key namespace), hidden queued proposals' keys included. Team administration ops (`SetTeamAccess`, `TeamShred`, `Compact`) may be proposed by the store owner only.
  - A queued proposal is visible to its author, the store owner, and principals who may read every lane it writes; listings show nothing else, not even a count. A team-layer rejection that only a hidden proposal causes is a bare `QueueConflict` at enqueue (not yet covered by a test: it needs a hidden proposal that changes a team-layer outcome while the local layer passes, e.g. through the state limit).
  - `prepare` builds one entry per call within the limits; the hook repeats prepare → sign → begin → push while proposals remain. A proposal depending on one in flight (`published`, not yet decided) waits for that outcome.
  - The policy version compared at the linearization point is opaque to the team crate; the daemon passes the epoch of the access document in force.
  - Outcomes come from the decided entries the store recorded during import (and log replay): `accepted`, `rejected{code}`; a published proposal whose commit the tracking ref does not contain after a fetch is queued again.
- **ReplicationLag and the strict gap (milestone 5).** `ReplicationLag` is an overlay on the SD13 summary, applied at read time: when a mirror of team *T* is in the read's L2-witness closure (the same support set as `ObservationLag`, Sem heads included; a direct read of a mirror included) and `live_pos["team:<hex>"]` is absent or differs from the branch's watermark, a summary of `PENDING(StructuralUnknown|Semantic)` or `CERTIFIED` becomes `PENDING(ReplicationLag)`; UNAVAILABLE, CONFLICTED, STALE and `ObservationLag` keep precedence. Nothing is stored in L0/L1/L2 or in `Dimensions`. The daemon expresses every lag cause of §8.3 (tip ahead of the watermark, pending announce, fetch in flight, stalled import) by what it puts in `live_pos` for the team scope; validation reports the scope in `Unknown{lag}` with code scopes. For `strict_no_aba`, the branch's in-memory change log records the epochs of `gap: true` watermark ops per team scope; a vector item that is a mirror of that team is a strict change when one falls after its `since_epoch`. A `team:` watermark advancing is not a strict change (only code anchors' scopes are). The oracle takes the gaps as a separate per-epoch input (`cert_validate_oracle_gaps`) that the test derives from the batches, because `Inputs` has an on-disk encoding and gains no field. `catch_up` writes through a `Writer` (the kernel, or the daemon's store), so tests can record every intermediate state. T116 (`crates/contextdb-team/tests/t116_certs.rs`) checks every case of §13 against the oracle.
- **Routing a write (milestone 5).** The kernel decides first (`WHAT_IF` on the single writer): a batch it accepts is local, and every P9 refusal (`Unauthorized(Read)` for a hidden name included) is returned as is. Only `ReservedNamespace`, `ReplicaReadOnly`, or `UnknownRef` on a batch naming a `team/` key, which the kernel decides after references resolve and after P9's checks, send the batch to `frontend::translate`. Classification is by write target: `CreateLogical` with a team key in the same team's lane, and `AddRevision`, `SetHead`, base changes and tags on a team record become `New`, `Revise`, `SetHead`, `SetBase`, `SetTags`; a rule whose conclusion is a team record becomes `AddRule` (premises and references as `Pin`/`Cur`/`Ref` of the same team, else `TeamDepOutside`); `Rebind` of such a rule is disable plus add. `ExpectHeads` is a read, not a target: in a team proposal its entries become `Expect` ops first (a local record there is `TeamDepOutside`); in a local batch an entry naming a team key that is only queued (in the author's overlay, not mirrored) is `Unpublished`. Team and local targets together, or two teams, are `MixedTeamBatch`. Not portable and kept as the kernel's refusal: a `Sem` premise in a team rule (O6), local `dirs` on a mirror (Q9), a team key in a non-team lane (`ReservedNamespace`). Expected values come from the team as this edge sees it — the replica with the author's readable queued proposals applied — because a mirror's base is the team *status* on the head only (§5.1) and mirrors carry no rules: a local batch can name a team rule only if it adds it. T109 (`crates/contextdb-team/tests/frontend.rs`).
- **The daemon (milestone 5).** Joined teams (`<data>/teams/<hex id>/`: the replica's anchor and decision log, the proposal queue, and `config` with the git work tree, the bound member and key, and the O5 publish settings) are opened at start and owned by the commit actor. `TeamImport` (at start, every `lag_check` of 2 s, and `ctx team sync`) imports each team's tracking refs and then brings every open branch up through the actor's own group commit, each batch carrying the mirror payloads from the replica; a refused branch is `ReplicaStalled` with the branch named, and import stops are recorded. Reads take `live_pos` for team scopes from shared in-memory state: the tracking ref's tip as last read, withheld while an announce is pending, a fetch is in flight or import is stopped. A write the kernel refuses as a team write (`Service::commit` and `ctx_commit`) goes to the actor's `TeamRoute`: translated against the author's overlays and queued, answered `Proposed{team, id}` (protocol 8: `Proposed`, `TeamLines`, `TeamSync`); a store with no joined team never takes this path. Team-layer refusals use `TxError::Team{code}`, whose `code` is the SPEC name the client sees.
- **`ctx team` (milestone 5).** `create` writes the genesis (`SetTeamAccess` with the creator as admin and member, `--lane`s written by `*members` and curated by `*admins`), signs it with `ssh-keygen -Y sign -n git` (a `.pub` key path uses the agent, `-U`; the signature is verified in-process against the key before use), pushes it with hooks off, then joins. `join` adds the fetch refspec, fetches in the caller's environment, takes the team id from the out-of-band genesis entry, builds the replica in the CLI process (before `ctxd` opens the directory), binds the member listed for `--key` (`NotTeamMember` otherwise; the half-built directory is removed), writes `config`, and asks a running `ctxd` to open and import it (`TeamOpen`). `publish` runs §7.2 steps 5–10 by hand — fetch and sync, prepare (a confirm listing prints its token), sign, begin (again on `PolicyChanged`/`QueueChanged`), push with hooks off (a non-fast-forward is `TeamPublishRefused` and a retry, at most 3), sync and show the outcomes. Tested with the real binary, real git and real SSH keys (`crates/contextdb-cli/tests/p10_team_cli.rs`).
- **The announce fence in `ctxd` (milestone 5).** `TeamAnnounce{team, ref, oid, pid}` records the announce in the pending set under the lock reads take, then acknowledges; `TeamWithdraw` removes it; `TeamNotify` queues an import without waiting. The durable form is `<data>/teams/<hex>/announce` (`ref oid pid` lines), appended and fsynced by the hook under an exclusive `flock` on `announce.lock`; `ctxd` reads every team's file after its sockets are bound and rewrites it, under the same lock, only to drop resolved lines, so a concurrent append is never lost. Each import resolves pending announces after reading the tip: one is done when the tracking ref contains its OID, or when its git process is gone (`kill(pid, 0)`) and the ref does not contain it. Tests: lag while an announce is pending, kept while its process lives, withdrawn, dropped for a dead process, resolved by the import that brings its OID.
- **The hook dispatcher (milestone 5).** Every ContextDB hook is one fixed script, `exec ctx git-hook <name> <hooks dir> "$@"`. It buffers the input of `pre-push` and `reference-transaction`, runs the user's original hook (kept as `<name>.contextdb-original`) with the same arguments and input, then the components registered in `<hooks dir>/contextdb.components`: `anchors` (P5a scan on `post-commit`, `post-checkout`, `post-merge`), `anchors-gate` (P5a `pre-push` gate), `team` (`reference-transaction`, `post-merge`, `pre-push`). `ctx anchors hooks install|uninstall` and `ctx team join` register components; a hook no component uses gets its original back, and P5a's old scripts are replaced in place. `reference-transaction`: a failing user hook is returned as is; in `prepared` every new team OID is appended to the announce file (fsynced, under the flock), then sent to a listening `ctxd` with a 500 ms acknowledgement bound — failure vetoes; `aborted` withdraws; `committed` notifies. `pre-push`: refuses deleting `refs/contextdb/team/*` and uploading `refs/contextdb/remotes/*`; runs a bounded sync (fetch and `TeamSync` within `push_timeout`); runs the P5a gate (lag only warns, O7); then, for teams whose remote name and URL this push uses, publishes under a `flock`ed `publish.lock` (the kernel releases a dead holder's) unless the push is a dry run. The push's arguments are found by walking up from the hook's parent (`/proc/<pid>/cmdline` on Linux; on macOS `ps -ww -o args=`, since `unsafe` is forbidden in the workspace and `KERN_PROCARGS2` needs it: an argument containing a space splits, which in git's push grammar can only add dry runs, never hide `-n`) and parsed with git's option grammar (`-n`, `--dry-run` and its abbreviations, grouped short options, `--no-dry-run`, `--`, `-o` values); an alias, or arguments not found, skips publish with a warning. Publish failures fail the code push only with `strict_push`. In a partial clone, `committed` also starts a detached `ctx team fetch-missing`: `git rev-list --objects --missing=print` over the new team commits (lazy fetching off) names what the clone lacks, which is fetched by OID through the promisor remote before `ctxd` is notified again (§8.1 step 2, Q13); `join` fetches the genesis entry's objects the same way, and retries an import that reports `ReplicaIncomplete` with the OIDs it names. Tested with real git and real processes: a dry run publishes nothing, a real push publishes and the proposal is accepted, a fetch on the other clone imports through the hooks alone, a blobless clone joins and its plain `git fetch` leaves no team object missing, and deleting the team ref is refused.
- **Leaving (milestone 5).** `ctx team leave --yes` asks `ctxd` (`TeamLeave`), which records `leaving` durably in the team's directory first, then writes on every open branch (archived ones are not written) one replica-channel batch retracting every base of the team's mirrors and setting the watermark to the sentinel `left`, then deletes the team's directory; the CLI then deletes the tracking refs and, with no team left in the data directory, the fetch refspec and the hook component. A team opened with `leaving` recorded is never imported or caught up: its next import finishes the leave (Q12). A `team:` scope whose watermark is `left` never lags, in the kernel and in the oracle, since nothing in it is base. Tests: the mirror and its dependents unsupported after a leave, the watermark `left`, the directory gone, a second leave refused; a recorded leave finished at the next start without mirroring a newer root entry.
- **`ctx team why` (milestone 5).** `TeamWhy` (store owner, admin socket) answers from the replica: the record's head, its status at the root with the replica's sequence, whether the head is base, and every rule concluding the head with its premises and references named `path@content` — never by replica ids (m15).
- **`ctx team rebuild` (milestone 5).** `TeamStore::rebuild` moves the decision log aside, recreates the replica from the trust anchor — the genesis, or the last verified checkpoint entry, which import now writes to `anchor` when it follows a successor (Q13) — imports from git, and deletes the old log only once the new one is complete (on failure it is put back). `ctxd` then catches every branch up with ordinary batches; a branch whose position the new history no longer holds is caught up across a gap (§5.2). The local op_log is never rewritten. Tests: a genesis rebuild reaches the same digest and history; an edge that followed a `Compact` has the checkpoint entry as its anchor and rebuilds from it; through the daemon, a rebuild leaves the branch's state and certification unchanged.
- **The `proposed` marker (milestone 5).** `Item` (protocol 8) carries `proposed: [(proposal id, local author)]`: the pending proposals that write the record, from the shared team state, which the actor refreshes whenever a queue changes (enqueue, publish steps, import). The single redaction point keeps, for a principal other than the store owner, only its own proposals — stricter than §6.2 allows (a proposal whose every lane the reader may read could be shown), never looser; no count of the others is shown. `ctx_read` shows the ids as `proposed`.
- **`ctx team compact`, `prune`, `rejoin` (milestone 6).** `TeamCompact` (admins; the bound member must be an admin of the team document) answers step 1 when no `Compact` is pending: Σc from the replica at the tip and a fresh proposal id, `ckpt(Σc, n+1)` written to the repository, and the unsigned `Compact` entry on `g<n>`. With a `Compact` pending it answers step 2: the replica is Σc, the checkpoint is rebuilt and checked against the committed tree (a mismatch is refused as a bug), and the unsigned successor `F` on `g<n+1>`. `ctx team compact` signs and pushes step 1, syncs, then step 2; `--resume` does step 2 only; a non-fast-forward successor push means another admin's successor stands; `--force-ref` replaces a squatted `g<n+1>`. `ctx team status` shows the generation, a digest prefix and `CompactPending`. `ctx team prune --yes` deletes the remote's generations older than the one this edge follows, with hooks off. `ctx team rejoin --genesis <oid>` is leave then join with the same repository, key and remote. Tested with real processes: a crash after step 1 (`CompactPending`), `--resume`, the follower at the same generation and digest, publishing in generation 1, and prune.
